## 3. Detailed Technical Reconciliations

### 3.1 Task 4A: Volume Reconciliation Policy & Unit Normalization

#### The Inconsistency
In `P2.2.9_TECHNICAL_VALIDATION_PLAN.md`, Section 6 contained conflicting guidance:
- The Cross-Source Reconciliation Matrix asserted: `Daily Vol Diff <= 1.0%` as a reconciliation constraint between Hugging Face 1m options and NSE daily bhavcopies.
- Section 6.1 asserted: `Discrepancies > 5% trigger an audit flag for missed intraday bars.`
- Neither threshold was calibrated against empirical data, and neither explicitly handled unit mismatches between contract counts and share quantities.

#### Primary Evidence & Repository Semantics
1. **Unit Differences:**
   - **Hugging Face (`thetrademarkk/india-index-options-1m`):** Volume is published in **share-equivalents** (number of contracts $\times$ contract lot size).
   - **Legacy NSE F&O Bhavcopy (`foDDMONYYYYbhav.csv`):** `CONTRACTS` represents **contract counts** (must be multiplied by lot size to obtain share-equivalents).
   - **UDiFF NSE F&O Bhavcopy (`BhavCopy_NSE_FO_...`):** `TtlTradgVol` represents **share quantities**.
2. **Coverage Differences:**
   - Provider intraday bar archives frequently exhibit missing minutes, session truncations (e.g. 15:00 cutoff on 2025-09-26), or illiquid strike dropouts, while the official daily bhavcopy aggregates all trades exchange-wide.
   - Enforcing a universal 1.0% or 5.0% threshold as a fatal gate causes legitimate datasets to be falsely rejected due to minor session dropouts or different trade matching windows.

#### Reconciled Conditional Policy
```
IF both datasets refer to the exact same contract (Symbol, Expiry, Strike, OptionType),
   on the exact same trading date,
   AND both volume figures have been converted to the same unit using a verified lot size:
       Compute:
           delta_abs = |Volume_intraday_sum - Volume_bhavcopy|
           delta_pct = delta_abs / Volume_bhavcopy
       Record delta_abs, delta_pct, raw units, normalized units, and lot-size provenance.
       Treat delta_pct as a DIAGNOSTIC / REVIEW FLAG ONLY.
       Neither 1.0% nor 5.0% shall operate as a universal fatal rejection threshold.
ELSE IF datasets are not unit-normalized, contract mapping is uncertain, session coverage differs,
        or the bar archive is known to be incomplete:
       Classify the comparison as NOT_COMPARABLE.
       Do not compute or interpret a misleading percentage difference.
       Do not reject the source based on this non-comparable comparison.
IF empirical calibration is conducted in a future milestone:
       Document the exact calibration sample, matching keys, denominator, unit, and threshold rationale.
       Until such calibration is approved by the repository owner, NO numeric volume tolerance operates as a gate.
```

### 3.4 Task 4D: Exact Decimal & Integer-Paise Tick Validation

#### The Inconsistency
Section 4.2 of `P2.2.9_TECHNICAL_VALIDATION_PLAN.md` formulated tick validation as:
```
price_paise = round(price * 100)
tick_paise = round(expected_tick * 100)
is_valid = (price_paise % tick_paise == 0)
```
Applying `round(price * 100)` before verifying decimal representation creates a precision loophole: a malformed price such as `₹18,245.054` or `₹18,245.05001` would be silently rounded to `1824505` paise and pass as valid on a ₹0.05 grid, masking sub-paise corruption.

#### Reconciled Exact Policy
```
IF input price is available as a string or exact Decimal (e.g. from CSV/JSON text):
    1. Parse into exact decimal representation D.
    2. Check scale: D must have at most 2 decimal places (D.as_tuple().exponent >= -2).
       IF exponent < -2 (e.g. 18245.054 has exponent -3):
           REJECT immediately: SUB_PAISE_PRECISION_ERROR.
    3. Compute exact integer paise:
           price_paise = int(D * 100)
           tick_paise = int(Decimal(str(expected_tick)) * 100)
    4. Check divisibility:
           is_valid = (price_paise % tick_paise == 0)
ELSE IF input price is binary floating-point (e.g. Parquet float64):
    1. Define strict tolerance: epsilon = 1e-5 (0.001 paise).
    2. Scaled value: s = price * 100.0
    3. Nearest integer paise: nearest_paise = round(s)
    4. Check proximity:
           IF |s - nearest_paise| > epsilon:
               REJECT immediately: FLOAT_SUB_PAISE_CORRUPTION.
    5. Check tick divisibility:
           is_valid = (int(nearest_paise) % int(round(expected_tick * 100)) == 0)
ELSE:
    Mark tick validation as UNVERIFIED; quarantine artifact from strict validation.
```

### 3.5 Task 4E: Participant-Wise OI Schema Column Alignment

#### The Inconsistency
In `P2.2.9_TECHNICAL_VALIDATION_PLAN.md`, Section 2.6 listed only 11 mandatory columns for Domain E:
`Date`, `Client_Type`, `Future_Index_Long`, `Future_Index_Short`, `Future_Stock_Long`, `Future_Stock_Short`, `Option_Index_Call_Long`, `Option_Index_Put_Long`, `Option_Index_Call_Short`, `Option_Index_Put_Short`, `Total_Long_Contracts`, `Total_Short_Contracts`.

It omitted the Option Stock columns, creating an internal contradiction with Section 6.2 and `P2.2.9.2`, which defined a 6-segment row-sum invariant:
$\text{Total Long} = \sum_{k=1}^6 \text{Long Segment}_k$.

#### Primary Evidence (`P2.2.8_FREE_DATA_SOURCE_INVENTORY.md:60` & Official Clearing Archives)
The official NSE Clearing `fao_participant_oi_{DDMMYYYY}.csv` contains exactly **15 columns**:
1. `Client Type`
2. `Future Index Long`
3. `Future Index Short`
4. `Future Stock Long`
5. `Future Stock Short`
6. `Option Index Call Long`
7. `Option Index Put Long`
8. `Option Index Call Short`
9. `Option Index Put Short`
10. `Option Stock Call Long`
11. `Option Stock Put Long`
12. `Option Stock Call Short`
13. `Option Stock Put Short`
14. `Total Long Contracts`
15. `Total Short Contracts`

#### Reconciled Specification
Section 2.6 of `P2.2.9_TECHNICAL_VALIDATION_PLAN.md` is updated to include all 15 columns.
The six long components strictly sum to `Total Long Contracts`:
$$\text{Total Long} = \text{FutIdxL} + \text{FutStkL} + \text{OptIdxCallL} + \text{OptIdxPutL} + \text{OptStkCallL} + \text{OptStkPutL}$$
The six short components strictly sum to `Total Short Contracts`:
$$\text{Total Short} = \text{FutIdxS} + \text{FutStkS} + \text{OptIdxCallS} + \text{OptIdxPutS} + \text{OptStkCallS} + \text{OptStkPutS}$$
Any row arithmetic mismatch triggers `FATAL_ROW_ARITHMETIC_ERROR`.
