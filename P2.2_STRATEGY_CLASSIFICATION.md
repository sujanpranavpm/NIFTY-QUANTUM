# P2.2.1 — Strategy Classification (for NIFTY CE/PE option-buying research)

Date: 2026-11-06 · Baseline commit: `03a5d27` (clean) · Budget: ₹0
Companion: `P2.2_STRATEGY_INVENTORY.md` (per-strategy evidence for every call below).

## 1. Classification question and rules

Each of the 20 registered strategies is classified against **one** question: *can this
implementation, as it exists, contribute to research on buying NIFTY index CE/PE options?*
Four buckets, exactly as specified in the task:

* **A — Suitable for options-buying research** (works now, no change, correct instrument).
* **B — Suitable only after modification** (sound, non-leaky logic that could drive index-option
  buying once re-targeted and given an option layer).
* **C — Not suitable for the current project** (wrong asset class / would require inventing logic).
* **D — Insufficient evidence to classify** (required data or behaviour is not present/observable,
  so a responsible call cannot be made yet).

Guardrails honoured (from the task and the project quality standards):
* **Order mechanics ≠ trading strategy.** `stop`, `stop_limit`, `trailing`, `bracket`, `OCO`,
  `limit` are *execution* devices inside these strategies; they are not themselves edges. A
  protective stop is not a reason the strategy suits options.
* **Equity ≠ options.** No strategy here trades a premium; each trades a cash-equity/FX/futures
  instrument at underlying granularity, with %-of-underlying stops/targets.
* **Underlying signal ≠ profitable option trade.** A directional index signal is a necessary but
  not sufficient condition; strike/expiry choice, theta/IV decay and premium-based risk are absent.
* **No logic invented, no profitability claimed.** Classification is about *fitness for research*,
  not about expected returns. The signals gate (`signals/gating.py`) approves on validation
  verdicts, never on a profit assertion.
* **Existing data & cost limits respected.** `transaction_costs_verified` is fail-closed; full
  daily universe fetch (T10) is outstanding; the only intraday data is 1m/5m/15m **option**
  candles; NIFTY **index** intraday and **point-in-time** membership do not exist in the repo.

## 2. Cross-cutting reality that sets bucket A to zero

For a strategy to be **A (suitable now)** it would have to (i) take a NIFTY-index (or option)
input, (ii) emit a CE/PE **buy** decision, (iii) select a strike/expiry and size in lots, (iv)
manage the exit on the **premium**, and (v) be costed by the option model. **None of the 20 does
any of (ii)–(v)**, and all 18 equity-applicable ones read **constituent-equity** bars rather than
the index (the index `^NSEI` is wired only as a benchmark). Therefore:

> **Bucket A = 0 strategies.** Every NSE-applicable strategy needs, at minimum, re-targeting to
> the NIFTY underlying and an option-execution + premium-risk + option-cost layer that does not
> exist yet. That is a *modification*, so those strategies land in **B**, not A.

## 5. Bucket rationale (why each non-B bucket)

**C — 19, 20 (not suitable).** Both are flagged `applicable_to_nse_equity=False` and sit in the
registry's `excluded_ids()`. Their sizing depends on `ContractSpec` FX lots / futures margin that
this engine deliberately does not model; their own adaptation notes state that a rupee/cash-equity
translation "measures a different thing" and would mean inventing a strategy. They are out of scope
for NIFTY option buying. Kept only for library completeness.

**D — 15, 16, 17 (insufficient evidence).** These cannot be responsibly bucketed until their data
prerequisites exist:
* `orders_15` needs **5m constituent-equity** candles; the repo has 5m only for **options**, which no
  strategy consumes. It also carries positions overnight (execution-context mismatch, flagged).
* `orders_16` needs a **30m** grid that the pipeline never produces, and its faithful-to-upstream
  **missing pending-order guard** lets identical stops stack, so realised size is indeterminate.
* `orders_17` ranks a **constituents basket**, not the NIFTY index, and uses a **current** (not
  point-in-time) membership snapshot — a survivorship leak that cannot be closed without a PIT
  universe history (absent). None of these is a data-free, index-direction option signal.

**A — 0 (none).** See §2: no strategy trades a premium or selects a strike/expiry.

## 6. Recommendations — what should enter *initial research screening*

Screening here means "eligible to be studied further for NIFTY CE/PE option buying after the option
layer is built", **not** "validated/profitable". Priority is by (a) how directly the signal gives
NIFTY-relevant **direction**, and (b) how reusable its exit structure is on a **premium**.

**Tier 1 — screen first (clean directional trend/breakout, reusable risk frame):**
1. **orders_12 (Bracket Trend)** — the SMA direction plus an explicit +6%/−3% OCO is the closest
   structural analogue to a premium take-profit/stop and a natural template for a CE/PE exit rule.
2. **orders_01 (Market SMA Crossover)** — the canonical, well-exercised (`test_signals.py`,
   `conftest.py`) directional cross; simplest to re-target onto the NIFTY index series.
3. **orders_18 (Signal-Change Rotation)** — same directional information at lower churn; needs a PE
   leg added for the downside flip.
4. **orders_05 / orders_07 (Stop & Stop-Limit Breakout)** — momentum bursts are the case where long
   options have the most convexity; their time-exit would be replaced by premium/Greeks exits.

**Tier 2 — screen after Tier 1 (same direction, different exit style — partly redundant):**
orders_06, orders_08, orders_09, orders_11, orders_04 (all restate the orders_01 direction with a
stop/trail/limit overlay; useful to compare exit styles, not new signals).

**Tier 3 — screen last / with caution (mean-reversion into a decaying instrument):**
orders_02, orders_10, orders_13, orders_03 — buying options on an oversold bounce works against
theta and demands tight timing; **orders_14** only after a directional CE-vs-PE rule is added.

**Deferred:** 15, 16, 17 — revisit only once their data prerequisites (underlying 5m/30m candles,
PIT universe) exist. **Excluded:** 19, 20.

## 7. Prerequisites before any B strategy can actually be screened for options

These are cross-cutting build items for a **later** P2.2 stage (explicitly *not* done now — no
modifications, no optimisation, no dashboard/broker work in this task):

1. **Option execution layer** in the strategy/engine: contract (strike+expiry) selection, lot sizing
   by `lot_size`, premium-priced fills, buy-CE / buy-PE order kinds. (Today only the *cost* module
   `options_costs.py` understands premium round trips; no strategy emits an option order.)
2. **Re-target the signal** from NIFTY50 constituents to the **NIFTY index** — daily index exists
   (`^NSEI`/`IDX_NSEI`); index **intraday** does not and would need generating.
3. **Premium-based risk**: convert %-of-underlying stops/targets and time-holds into premium/Greeks
   (and expiry/theta aware) exits.
4. **Data**: full-universe daily fetch (T10) for any constituent-derived study; underlying index
   1m/5m/15m candles for intraday option signalling.
5. **Cost/validation**: the option readiness gate is **fail-closed** (`transaction_costs_verified`
   False; 2 slab-era `exchange_txn` rows `estimated`), so option results remain **modelling-only /
   not strict-financial-validation** until that gate is legitimately satisfied — a limit to respect,
   not a defect to paper over.
