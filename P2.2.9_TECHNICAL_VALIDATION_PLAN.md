## 1. Purpose and Operational Philosophy

This document defines the technical data engineering, validation, reconciliation, and provenance architecture required before any raw market or macro data can be ingested into `nifty_quantum`.

In quantitative finance, ingestion errors, survivorship bias, silent corporate splits, unannounced exchange schema changes, and unit mismatch errors propagate directly into strategy models, generating spurious statistical significance or catastrophic backtest alpha inflation. To prevent this, the repository mandates a **Strictly Fail-Closed Validation Architecture**: any ingested batch, daily file, or candle series failing schema compliance, range bounds, trading calendar alignment, or unit reconciliation must be rejected immediately prior to feature generation or model consumption.

## 2. Ingestion Schemas & Mandatory Column Specifications

Every candidate source must be parsed and mapped into standardized internal schemas before persistence.

### 2.1 Domain K: Daily F&O Bhavcopy (Dual-Schema Specification)

Due to the SEBI/NSE Unified Data Integration Format (UDiFF) mandate implemented on **July 8, 2024**, ingestion engines must handle two mutually exclusive formats.

#### Legacy Schema (Pre-July 8, 2024)
- **File Signature:** `fo{DD}{MON}{YYYY}bhav.csv` inside `.zip`
- **Mandatory Columns & Target Types:**
  1. `INSTRUMENT`: String (Valid values: `OPTIDX`, `FUTIDX`, `OPTSTK`, `FUTSTK`)
  2. `SYMBOL`: String (e.g., `NIFTY`, `BANKNIFTY`)
  3. `EXPIRY_DT`: Date (Format: `DD-MMM-YYYY`, e.g., `28-Oct-2021`)
  4. `STRIKE_PR`: Float64 (₹0.00 for Futures, positive multiple of 50 for NIFTY options)
  5. `OPTION_TYP`: String (`XX` for Futures, `CE` for Call, `PE` for Put)
  6. `OPEN`: Float64 ($\ge 0.00$)
  7. `HIGH`: Float64 ($\ge 0.00$)
  8. `LOW`: Float64 ($\ge 0.00$)
  9. `CLOSE`: Float64 ($\ge 0.00$)
  10. `SETTLE_PR`: Float64 ($> 0.00$, daily official settlement price)
  11. `CONTRACTS`: Int64 ($\ge 0$, number of contracts traded)
  12. `VAL_INLAKH`: Float64 ($\ge 0.00$, turnover in Lakhs INR)
  13. `OPEN_INT`: Int64 ($\ge 0$, open interest in contracts)
  14. `CHG_IN_OI`: Int64 (signed integer, change in open interest)
  15. `TIMESTAMP`: Date (Format: `DD-MMM-YYYY`)

#### Unified Schema (UDiFF, Post-July 8, 2024)
- **File Signature:** `BhavCopy_NSE_FO_0_0_0_{YYYYMMDD}_F_0000.csv` inside `.zip`
- **Mandatory Columns & Target Types:**
  1. `TradDt`: Date (Format: `YYYY-MM-DD`)
  2. `FinInstrmTp`: String (`FTO` for Futures, `OPO` for Options)
  3. `TckrSymb`: String (e.g., `NIFTY`)
  4. `XprtnDt`: Date (Format: `YYYY-MM-DD`)
  5. `StrkPric`: Float64 ($\ge 0.00$)
  6. `OptnTp`: String (`CE`, `PE`, or blank/`NA` for Futures)
  7. `OpnPric`: Float64 ($\ge 0.00$)
  8. `HghPric`: Float64 ($\ge 0.00$)
  9. `LwPric`: Float64 ($\ge 0.00$)
  10. `ClsPric`: Float64 ($\ge 0.00$)
  11. `SttlmPric`: Float64 ($> 0.00$)
  12. `OpnIntrst`: Int64 ($\ge 0$, open interest in shares)
  13. `ChngInOpnIntrst`: Int64 (change in open interest in shares)
  14. `TtlTradgVol`: Int64 ($\ge 0$, total shares traded)
  15. `TtlTrfVal`: Float64 ($\ge 0.00$, total turnover in INR)
  16. `ISIN`: String (12-character alphanumeric exchange identifier)

## 3. Completeness & Calendar Alignment Strategy

The Indian capital markets operate on a regulated holiday and session schedule that must be strictly enforced.

### 3.1 Exchange Holiday Calendar Reconciliation
- **Reference Calendar:** Official NSE Capital Markets & Derivative Markets Holiday List (published annually by NSE Clearing/Exchange circulars).
- **Validation Rule:**
  - An EOD file is **expected** for every Monday through Friday, excluding official NSE declared trading holidays.
  - If a standard weekday has no bhavcopy and is **not** on the official holiday schedule, the pipeline must raise a `CRITICAL_DATA_GAP` alert and fail-closed.
  - If a file exists on an official holiday, it must be flagged for manual review (possible ad-hoc disaster recovery or simulated test file accidentally uploaded to archives).

### 3.2 Special Trading Sessions & Disruptions
- **Diwali Muhurat Trading:** A ceremonial 1-hour evening trading session occurring on Diwali/Laxmi Pujan (typically 18:00 to 19:15 IST).
  - Validation: Valid trading day, but volume and turnover are typically 10–20% of normal days. Ingestion must tag this date with `is_special_session = True` so that rolling volatility and average volume filters do not treat the day as an anomaly or liquidity collapse.
- **Disaster Recovery / Special Live Trading Days:** Occasional Saturday trading sessions (e.g., switchover to DR site on March 2, 2024, and May 18, 2024).
  - Validation: Pipeline must maintain a `special_trading_sessions.csv` master to recognize legitimate Saturday trading files.
- **Trading Halts / Technical Glitches:** e.g., the February 24, 2021 telecom link failure which halted trading between 11:40 and 15:30 IST, followed by extended trading until 17:00 IST.
  - Validation: EOD daily bhavcopy exists, but intraday 1-minute data will exhibit a zero-volume plateau. The intraday validator must accommodate documented market-wide halts without failing the batch.

## 4. Rigorous Numerical Integrity Checks

Every parsed record must pass mathematical sanity constraints:

### 4.1 OHLC Structural Containment
For every candle (both intraday 1-minute and daily EOD):
$$\text{Low} \le \min(\text{Open}, \text{Close}) \le \max(\text{Open}, \text{Close}) \le \text{High}$$
Any record where $\text{High} < \text{Open}$, $\text{High} < \text{Close}$, $\text{Low} > \text{Open}$, or $\text{Low} > \text{Close}$ must cause immediate batch rejection.

### 4.2 Tick Size Validation (Instrument-Specific Specification)
- **No Universal ₹0.05 Rule:** Tick size must be dynamically resolved from an effective-dated, instrument-specific reference specification (`data/reference/nifty_tick_sizes.csv`):
  - **NIFTY Index Options Traded Prices (Open, High, Low, Close):** Expected tick size is **₹0.05** (verified 100% on-grid across all 318 official cached bhavcopy dates and all historical provider files).
  - **NIFTY Index Options Settlement Prices (`SttlmPric` / `SETTLE_PR`):** Expected tick size is **₹0.05** prior to August 3, 2026. Effective August 3, 2026, under NSE circular `NSE/FAOP/67135`, settlement prices follow the index-level price-step ladder: ₹0.05 ($S \le 15,000$), **₹0.10** ($15,000 < S \le 30,000$), and ₹0.20 ($S > 30,000$).
  - **Stock Futures & Stock Options:** Under NSE circular `NSE/FAOP/67134`, single-stock derivatives inherit the dynamic tick size of the underlying security in the Capital Market (CM) segment.
  - **Cash Equities (CM Segment):** Resolved dynamically from security master records.
- **Exact Decimal & Integer-Paise Validation (Floating-Point Modulo Avoidance):**
  To avoid IEEE 754 precision failures and prevent naive rounding from masking sub-paise corruption (e.g. `100.004` rounded into `10000`), tick adherence must follow a strict two-stage decimal policy:
  1. **Decimal Precision Pre-Check:**
     - For string/decimal sources (CSV/JSON): Parse into an exact decimal. Verify that scale is $\le 2$ decimal places. Any value with sub-paise precision (e.g., 3+ decimal digits like `₹18,245.054`) must be rejected immediately (`SUB_PAISE_PRECISION_ERROR`).
     - For binary float sources (Parquet float64): Evaluate against an explicit tolerance $\epsilon = 10^{-5}$ ($0.001$ paise). Compute scaled value $s = \text{price} \times 100$. If $|s - \text{round}(s)| > \epsilon$, reject immediately (`FLOAT_SUB_PAISE_CORRUPTION`).
  2. **Integer Divisibility Check:**
     Once verified representable in whole paise, compute exact integer values:
     $$\text{price\_paise} = \text{int}(\text{round}(\text{price} \times 100))$$
     $$\text{tick\_paise} = \text{int}(\text{round}(\text{expected\_tick} \times 100))$$
     $$\text{is\_valid} = (\text{price\_paise} \pmod{\text{tick\_paise}} == 0)$$

### 4.3 Zero-Volume and Zero-OI Handling (Strict Completeness Taxonomy)
- **Zero Imputation Policy:** Tradable OHLC prices must **never** be forward-filled or synthesized across missing intervals. Inactive intervals on option strikes must be categorized strictly according to `nifty_quant/derivatives/completeness.py`:
  - `NO_TRADES`: Exchange reports contract as listed, but zero trades occurred during the interval. (Valid market state; no candle synthesized).
  - `MISSING_DAYS`: Exchange reports positive traded volume, but intraday file carries zero bars. (Data defect; fail-closed rejection).
  - `TRUNCATED_SESSION`: Intraday bars cease prematurely prior to 15:25 IST. (Session defect; excluded from intraday execution).
  - `MARKET_WIDE_HALT`: Documented exchange halts (e.g., February 24, 2021). (Accepted upon calendar/circular corroboration).
- **Open Interest Handling:**
  - `Zero OI` (`open_interest == 0`): Represents an unrecorded or missing provider observation (`PRESENT_WITHOUT_OI`), **not** that open positions ceased to exist. Must be excluded from OI-derived features and never forward-filled.
  - `Unchanged OI`: Repeated OI across consecutive bars is normal during quiet trading intervals and must not be flagged as stale.

### 4.4 Positive Price Bounds
- Options: $\text{Price} \ge 0.00$.
- Underlyings / Futures: $\text{Price} > 0.00$. (Negative commodity futures occurred during WTI April 2020, but Indian equity index futures are strictly bounded $> 0$).

## 5. Unit Reconciliation & Contract Scaling Architecture

A major source of historical data corruption in Indian derivatives is the unannounced shift in contract lot sizes and the transition from contract counts to share counts.

### 5.1 Historical NIFTY 50 Lot Size Regimes & Contract Cohort Overlaps
NSE periodically revises market lot sizes under SEBI mandate. Crucially, revisions **do not apply uniformly across all active contracts on a calendar date**. On every lot-size revision date, the exchange lists two lots simultaneously: newly issued expiry cohorts trade at the new lot size, while already-listed contracts retain their original lot size until expiry.

Evidence from official circulars (`FAOP54334`, `FAOP64506`, `FAOP68747`), `fo_mktlots.csv`, `logs/lot_schedule.txt`, and UDiFF bhavcopies:

```
+-------------------+-------------------+----------+-----------+---------------------------------------------------------------------------------------+
| Window Period     | Cohort Nature     | Modal Lot| Co-Ex. Lot| Documented Exchange Mechanism & Cohort Transition                                     |
+-------------------+-------------------+----------+-----------+---------------------------------------------------------------------------------------+
| Pre-2021-12-01    | Historical Inferred| 75       | None      | Inferred from provider minimum traded volume; no official pre-2024 archive arbiter.   |
| 2021-12-01..2024-04-29 | Pre-April 2024| 50       | None      | Modal lot 50 contiguously covers through 2024-04-29 (test_lot_reference.py). In the  |
|                   |                   |          |           | 32 cached bhavcopies, observation ends 2024-04-25; 04-26..04-29 unobserved/inferred.  |
| 2024-04-30..2024-11-21 | Cut to 25     | 25       | None      | Board lot cut to 25. Sole lot listed on NIFTY option rows in this span.               |
| 2024-11-22..2025-01-30 | Transition 1  | 25 -> 75 | 25 AND 75 | Lot 75 introduced for new expiries on 2024-11-22 (142 rows lot 75, 1,574 rows lot 25).|
|                   |                   |          |           | Dual lots co-existed daily until 2025-01-30 when all lot 25 contracts expired.       |
| 2025-01-31..2025-10-29 | Raised to 75  | 75       | None      | Lot 75 sole lot listed across all NIFTY option rows.                                 |
| 2025-10-30..2026-01-02 | Transition 2  | 75 -> 65 | 65 AND 75 | Lot 65 introduced for new expiries on 2025-10-30 (146 rows lot 65, 1,448 rows lot 75).|
|                   |                   |          |           | Dual lots co-existed daily until 2026-01-05 when lot 65 became sole listed lot.      |
| 2026-01-05..Present| Cut to 65        | 65       | None      | Current active lot in NSE fo_mktlots.csv.                                             |
+-------------------+-------------------+----------+-----------+---------------------------------------------------------------------------------------+
```

### 5.2 Contract-Level Lot Size Resolution & Harmonization
1. **Contract-Level Resolution Key:** Lot size must be resolved per contract using the 4-tuple key:
   $$\text{ContractKey} = (\text{Symbol}, \text{ExpiryDate}, \text{StrikePrice}, \text{OptionType})$$
2. **Authority Hierarchy:**
   - **Primary Authority:** Observed per-contract row lot (`NewBrdLotQty` in UDiFF bhavcopy). (`estimated = False`).
   - **Secondary Authority:** Specific contract cohort mapping from expiry issuance circulars. (`estimated = False`).
   - **Tertiary Fallback:** Modal date regime lookup (`data/reference/nifty_lot_history.csv`). Must be flagged with `estimated = True` and `basis = BASIS_DATE_REGIME`.
   - **Fail-Closed Rule:** Any contract traded during dual-lot transition windows whose expiry cohort cannot be mapped unambiguously must be marked `UNKNOWN` and rejected from strict financial validation.
3. **Harmonization Formulas:**
   - **Legacy Bhavcopy (Pre-July 8, 2024):**
     $$\text{Volume}_{\text{shares}} = \text{CONTRACTS} \times \text{LotSize}(\text{ContractKey})$$
     $$\text{OpenInterest}_{\text{shares}} = \text{OPEN\_INT} \times \text{LotSize}(\text{ContractKey})$$
   - **UDiFF Bhavcopy (Post-July 8, 2024):**
     $$\text{Volume}_{\text{contracts}} = \frac{\text{TtlTradgVol}}{\text{LotSize}(\text{ContractKey})}$$
     $$\text{OpenInterest}_{\text{contracts}} = \frac{\text{OpnIntrst}}{\text{LotSize}(\text{ContractKey})}$$
   - Pipeline must store **both** `contracts_count` and `shares_count` with explicit column naming (`volume_contracts`, `volume_shares`).

## 6. Cross-Source Reconciliation Strategy

Ingestion data must be verified across independent sources to prevent systematic bias.

```
+---------------------------------------------------------------------------------------------------+
| Cross-Source Reconciliation Matrix                                                                |
+------------------------------------+--------------------------------+-----------------------------+
| Dataset A (Candidate)              | Dataset B (Arbiter / Baseline) | Reconciliation Constraint   |
+------------------------------------+--------------------------------+-----------------------------+
| Hugging Face 1m Options (SRC-L1)   | NSE Daily Bhavcopy (SRC-K1)    | Date & Expiry Existence     |
| Hugging Face 1m Options EOD Sum    | NSE Daily Bhavcopy Total Vol   | Diagnostic Volume Drift     |
| Hugging Face 1m Close (15:29)      | NSE Daily Bhavcopy Last/Close  | Diagnostic Price Drift      |
| Cash Bhavcopy NIFTY 50 Synthetic   | NIFTY 50 Index Close (SRC-D1)  | Basket Diff <= 0.25%        |
| India VIX (SRC-A1)                 | Model ATM IV (SRC-B-INTERNAL)  | Directional Corr >= 0.85    |
+------------------------------------+--------------------------------+-----------------------------+
```

### 6.1 Intraday vs. EOD Bhavcopy Arbiter Rule
- **The Daily NSE Bhavcopy (SRC-K1) is the absolute authority for trading day completeness and settlement truth.**
- If Hugging Face 1-minute data has records for a date that does **not** exist in the NSE official bhavcopy, that date is rejected as an artifact.
- **Conditional Volume Reconciliation Policy:**
  - **Unit Alignment Prerequisite:** Hugging Face intraday volume is expressed in **share-equivalents** (contracts $\times$ lot size), whereas Legacy F&O Bhavcopy `CONTRACTS` indicates **contract counts**, and UDiFF `TtlTradgVol` indicates **shares**. Both series must be normalized to a shared unit using verified contract lot sizes prior to comparison.
  - **Diagnostic Status:** If the contract mapping, unit normalization, and session coverage are complete, compute absolute volume difference $\Delta_{\text{vol}} = |\sum v_t - V_{\text{bhavcopy}}|$ and percentage drift. This metric operates as a **DIAGNOSTIC / REVIEW FLAG ONLY**. Neither 1.0% nor 5.0% shall operate as a universal fatal rejection threshold until an empirical calibration sample is formally approved.
  - **Incomparable Archives:** If units cannot be normalized, lot size is unverified, or the session is truncated (e.g. 15:00 cutoff on 2025-09-26), the comparison is marked **`NOT_COMPARABLE`** and does not trigger dataset rejection.
- **Diagnostic EOD Close vs 30-Minute VWAP Comparison:**
  - Official exchange `Close` (`ClsPric`) is the volume-weighted average price (VWAP) of all trades in the last 30 minutes of trading (15:00 to 15:30 IST), whereas 15:29 candle close is the last traded price in that 1-minute interval.
  - They are fundamentally different metrics with distinct trade universes and weightings. In volatile index options, legitimate divergence can exceed 10–20%.
  - This comparison is classified as **DIAGNOSTIC ONLY**, not a hard rejection threshold. The pipeline verifies that the 15:29 bar close falls within the day's high-low range ($\text{LwPric}_{\text{EOD}} \le \text{Close}_{15:29} \le \text{HghPric}_{\text{EOD}}$) and records percentage drift as an informational metric.

### 6.2 Participant Open Interest Reconciliation
- **Report Structure & Semantics:**
  - In Domain E (`fao_participant_oi`), data is reported across 4 client categories: `Client`, `DII`, `FII`, and `Pro`.
  - Within each participant category, Long positions NEVER equal Short positions (e.g., institutional hedging produces net short futures).
- **Strict Row-Level Arithmetic Invariant:**
  - For each participant row $i$, the reported totals must equal the sum of the segment columns:
    $$\text{Total Long}_i = \sum_{k=1}^6 \text{Long Segment}_{i, k}$$
    $$\text{Total Short}_i = \sum_{k=1}^6 \text{Short Segment}_{i, k}$$
  - Any internal row discrepancy indicates corrupt records and causes immediate batch rejection (`FATAL_ROW_ARITHMETIC_ERROR`).
- **Market-Wide Aggregate Equality as Diagnostic Metric:**
  - Cross-participant net positions ($\sum \text{Total Long}_i \approx \sum \text{Total Short}_i$) are monitored as an **INFORMATIONAL DIAGNOSTIC**. Because public clearing reports may omit unallocated clearing member positions or apply post-settlement adjustments without public reconciliation documentation, aggregate discrepancies must be logged as warnings rather than triggering fatal pipeline aborts.

## 8. Explicit Fail-Closed Acceptance and Rejection Rules

The ingestion engine must follow strict binary gating:

```
+---------------------------------------+-----------------------------+------------------------------------+
| Anomaly / Condition                   | Severity                    | Pipeline Action                    |
+---------------------------------------+-----------------------------+------------------------------------+
| Missing mandatory header column       | FATAL                       | Fail-Closed: Immediate Rejection   |
| Date mismatch in filename vs row data | FATAL                       | Fail-Closed: Immediate Rejection   |
| OHLC containment violation            | FATAL                       | Fail-Closed: Immediate Rejection   |
| Negative volume or open interest      | FATAL                       | Fail-Closed: Immediate Rejection   |
| Non-tick-aligned price (integer-paise)| FATAL                       | Fail-Closed: Immediate Rejection   |
| Participant row arithmetic mismatch   | FATAL                       | Fail-Closed: Immediate Rejection   |
| Unmapped lot-size contract cohort     | FATAL                       | Fail-Closed: Reject from strict use|
| Missing SHA256 / provenance metadata  | FATAL                       | Fail-Closed: Quarantine Batch      |
| Intraday bar gap (no trades)          | ACCEPTABLE                  | Tag NO_TRADES; zero imputation     |
| EOD price drift vs 30m VWAP           | DIAGNOSTIC                  | Log metric; verify EOD range bounds|
| Participant aggregate long != short   | DIAGNOSTIC                  | Log diagnostic discrepancy warning |
+---------------------------------------+-----------------------------+------------------------------------+
```

No heuristic guessing, forward-filling across unannounced schema breaks, or silent coercion of corrupt data is permitted in `nifty_quantum`.
