# P2.2.5.1 — Screening Integrity Audit

Date: 2026-11-06 · Baseline commit: `03a5d27` (HEAD unchanged) · Continues from the **P2.2.5**
working tree · Budget: ₹0.

**Scope.** A narrow *integrity* audit of the P2.2.5 screening. Nothing here optimises a
parameter, modifies a strategy or a validation threshold, or reads the protected holdout to
select anything. The three items asked were: (1) the TP/SL discrepancy, (2) the naive-ATM
`n=855` benchmark, (3) the `orders_12`/`orders_01`/`orders_18` identical-signal finding.

> **Headline.** Two material integrity issues and one confirmation:
> 1. **The exit convention that was *run* (±30% / −30%, uniform, 1:1) is NOT the exit
>    convention that was *approved* (TP **+15%** / SL **−8%**, ratio-preserving — `orders_12`
>    → **+16%/−8%**, ≈2:1).** The divergence was introduced at the **P2.2.3 adapter-implementation
>    step** and is mislabelled *"unchanged"* in the P2.2.5 report. It is not a look-ahead/holdout
>    selection (the ±30% band is a symmetric a-priori convention), but it *is* an unapproved
>    methodology change that **moves every candidate's result**.
> 2. **The `n=855` naive-ATM benchmark is an unconditional buy-ATM-every-day series — its entries
>    do NOT match any candidate's signal dates or contracts** (1,030 distinct entry dates vs 9–35
>    per candidate). It is a valid *market-behaviour* yardstick but not a like-for-like exit-rule
>    comparison. A clearly labelled **signal-matched hold-to-expiry** comparison (identical
>    entries/contracts/costs, only the exit rule changed) is provided below and reverses the
>    apparent verdict: on their own signals, **every candidate's hold-to-expiry return beats the
>    all-days benchmark**, and the value-destroying element is the TP/SL band, not the signals.
> 3. **Confirmed:** `orders_12`, `orders_01`, `orders_18` raise a **byte-identical signal array**.
>
> The original P2.2.5 report, artifacts and logs are **preserved verbatim**; the counterfactuals
> below are recomputed with the *unchanged* modules and are labelled as audit comparisons, not new
> parameter choices.

Reproduce: `$env:PYTHONPATH='.'; python scripts/_p2251_audit.py` → `logs/p2251_audit.txt`

## 1. TP/SL discrepancy — approved vs run

### 1.1 What was approved

| Source | Approved exit convention |
|--------|--------------------------|
| `P2.2_OPTIONS_ADAPTATION_DESIGN.md` §L168-170, §L248 | "fixed premium-percentage band declared up front (**TP +15% / SL −8%** … orders_12's 2:1 [preserved]" |
| `P2.2.2.1_METHODOLOGY_RECONCILIATION.md` §3.4 L141-144 | "TP **+15%** / SL **−8%** … applied identically to all five candidates, **preserving each strategy's own reward:risk ratio** where it defines one (**orders_12 → 2:1 honoured by a +16%/−8% variant**, still ratio-locked, not result-tuned)" |
| `P2.2.2.1_METHODOLOGY_RECONCILIATION.md` §5 L213 | "premium SL/TP band declared fixed (**+15%/−8%, ratio-preserving**)" |

So the approved convention is **asymmetric** (+15 / −8, ≈ 2:1), and where a strategy already
defines a reward:risk ratio it is **preserved per-strategy** (`orders_12` → +16/−8).

### 1.2 What was actually implemented and run

| Location | Value |
|----------|-------|
| `nifty_quant/options/pipeline.py` `ExitConvention` L51-52 | `stop_fraction = 0.30`, `target_fraction = 0.30` |
| `P2.2.3_OPTIONS_BUYING_ADAPTER.md` §4 L130-133 | "`ExitConvention(stop_fraction=0.30, target_fraction=0.30 …)`: stop = `entry_open×0.70`, target = `entry_open×1.30` … a convention applied identically to every candidate" |
| `scripts/_p225_screen.py` L188 / L332 | `AdapterConfig(resolution=…)` — the default `ExitConvention()` is used; **no override anywhere** |
| `P2.2.5_INITIAL_SCREENING_REPORT.md` §1 L35 | Exits row reads `+30% / −30%` … "ExitConvention, **unchanged**" |

The run convention is **symmetric** (±30%, 1:1) and **uniform** across all five candidates — a
**three-part** deviation from the approved design: (a) magnitude (30 vs 15/8), (b) shape
(1:1 vs ≈2:1), (c) uniform vs ratio-preserving-per-strategy.

### 1.3 When the change occurred, and whether it was approved

* The **entire P2.2.x layer is untracked** (`nifty_quant/options/`, `scripts/_p22*.py`,
  `P2.2*.md` all show `??` in `git status`), so the change cannot be dated from `git blame`. The
  document/code sequence is the only available evidence, and it is unambiguous:
  - Approved (+15%/−8%, ratio-preserving): `P2.2_OPTIONS_ADAPTATION_DESIGN.md`,
    `P2.2.2.1_METHODOLOGY_RECONCILIATION.md`.
  - **First appearance of ±30%/30%: `P2.2.3_OPTIONS_BUYING_ADAPTER.md` §4** (the adapter
    delivery) and the committed default in `pipeline.py`.
* Therefore **the change happened at the P2.2.3 adapter-implementation step**, between methodology
  approval (P2.2.2.1) and delivery (P2.2.3).
* **It was not approved.** No document records a decision to move from +15%/−8% to ±30%/30%, and the
  deviation was not flagged. The P2.2.3 rationale ("applied identically to every candidate so exits
  are comparable") justifies *uniformity*, not the *value* or the *symmetric shape*, and it silently
  drops the ratio-preserving requirement for `orders_12`.
* **It was not selected on the holdout.** ±30%/30% is a fixed symmetric a-priori convention; the
  report states it "not tuned" and no parameter search touched it. This is a **governance /
  documentation-integrity** defect (an unapproved substitution reported as "unchanged"), **not** a
  look-ahead-tuning defect.
* The report's **"unchanged"** label at §1 L35 is **factually incorrect** relative to the approved
  methodology and should be corrected to "deviation from the approved +15%/−8% (see P2.2.5.1)".

### 1.4 Materiality — the deviation changes the numbers (audit counterfactual, not a new choice)

Recomputed with the unchanged modules, BASELINE, Development+Validation only (holdout untouched).
`expectancy_ret` = mean `net_pnl / (entry_premium × lot_size × lots)` — the same metric the report's
§9 naive-ATM comparison uses. The **as-run ±30% column reproduces the published report exactly**
(`orders_12` −0.049948, `orders_05` +0.023478, `orders_07` +0.038109), which validates the harness.

| Candidate | As-run ±30% exp_ret | As-run exp_net | **Approved +15/−8 exp_ret** | **Approved exp_net** | Approved PF | Approved win |
|-----------|:---:|:---:|:---:|:---:|:---:|:---:|
| orders_12 (→ +16/−8) | −0.04995 | +235.1 | **−0.07590** | −66.4 | 0.882 | 0.333 |
| orders_01 | −0.04995 | +235.1 | **−0.07921** | −97.6 | 0.826 | 0.333 |
| orders_18 | −0.04995 | +235.1 | **−0.07921** | −97.6 | 0.826 | 0.333 |
| orders_05 | +0.02348 | −113.9 | **−0.01016** | −122.4 | 0.759 | 0.371 |
| orders_07 | +0.03811 | +161.3 | **+0.00314** | −79.4 | 0.834 | 0.455 |

**Finding.** The tighter, asymmetric approved band is **worse** than the as-run ±30% on every
candidate. Had the approved methodology been run, the "break-even on BASELINE?" gate would have
flipped for `orders_07` (net −79.4 < 0) and `orders_12` (net −66.4 < 0), changing §10 classification
inputs. This is why the discrepancy matters: **the as-run result is not the result the approved
methodology would have produced.** No recommendation to adopt either value is made here — restoring
the approved +15%/−8% requires an explicit, documented decision (P2.2.6), not a silent edit.

## 2. Naive-ATM benchmark integrity

### 2.1 Why it reports 855 trades

`scripts/_p225_screen.py::naive_atm()` iterates over **every day in the index daily series**
(`for day_ts in daily.index`), and for each day selects the ATM **CE** and runs it to expiry with an
empty `ExitRules()` — it is **not driven by any candidate's signals**. From
`artifacts/p225/naive_atm_baseline.csv`:

* BASELINE rows = **1,030** with **1,030 distinct entry dates** → one unconditional entry per session
  over the whole calendar.
* Restricting to Development+Validation leaves **873** rows; the metric helper drops **18 `UNRESOLVED`**
  (expiry on an unobservable bar) → **855** trades. This reconciles exactly with the published
  §9 line (`n=855, win 41.6%, PF 1.133, expectancy +₹479.4, +6.06% per unit premium`).

### 2.2 Do its entries match each candidate's actual signals? No.

| Series | Distinct Dev+Val entries | Entry basis |
|--------|:---:|---|
| naive-ATM benchmark | **855** | every session day, unconditional |
| orders_12 / 01 / 18 | 9 | own `flat→long` signals only |
| orders_05 | 35 | own signals |
| orders_07 | 33 | own signals |

The benchmark shares only the *contract-selection rule* and *costs* with the candidates; its **entry
dates are disjoint from the candidates' event-driven entries** (1,030 calendar days vs 9–35 signal
days). It answers *"what does holding ATM NIFTY calls to expiry every day earn?"*, not *"what would
this candidate earn if it held to expiry instead of using the ±30% exits?"*. Comparing a candidate's
signal-timed expectancy to it (report §9/§10 "beats naive-ATM") is therefore **apples-to-oranges**.
The original all-days benchmark is **retained** as a market-behaviour reference; the like-for-like
comparison is below.

### 2.3 Signal-matched hold-to-expiry (identical entries/contracts/costs, only the exit changed)

For each candidate, its own signals are entered on the same session (D+1), the same contract is
selected, the same costs apply — the **only** change is replacing the as-run ±30% TP/SL with
`ExitRules()` (hold to expiry). BASELINE, Dev+Val.

| Candidate | n | win | PF | exp_ret (±30% as-run) | **exp_ret (hold-to-expiry)** | **exp_net (hold-to-expiry)** |
|-----------|:-:|:---:|:---:|:---:|:---:|:---:|
| orders_12 | 9 | 0.444 | 1.798 | −0.04995 | **+0.13670** | +2,301.3 |
| orders_01 | 9 | 0.444 | 1.798 | −0.04995 | **+0.13670** | +2,301.3 |
| orders_18 | 9 | 0.444 | 1.798 | −0.04995 | **+0.13670** | +2,301.3 |
| orders_05 | 33 | 0.424 | 1.297 | +0.02348 | **+0.23138** | +947.8 |
| orders_07 | 32 | 0.344 | 1.603 | +0.03811 | **+0.25909** | +1,442.8 |

(`n` falls by a trade or two versus §1.4 for `orders_05`/`orders_07` because holding to expiry turns
a few expiry-on-missing-bar cases into `UNRESOLVED`, which the P&L metric excludes — the same
fail-closed behaviour the engine already pins.)

**Findings.**
* Under the **correct like-for-like** comparison, **every candidate's hold-to-expiry expectancy
  (+13.7% to +25.9%) exceeds the all-days benchmark's +6.06%**, and exceeds its own ±30% result by a
  wide margin. The report's qualitative claim — *"the exits, not the signals, are the weak link"*
  (§11) — is **directionally correct and, when measured properly, strong**.
* The comparison that drove the §10 "beats naive-ATM = ✗" for the candidates was **not** exit-for-exit
  matched: it scored signal-timed TP/SL entries against unconditional daily hold entries. A future
  screening should decide the "beats naive-ATM" gate against this **signal-matched** series.
* This is diagnostic only: it changes no classification in P2.2.5 retroactively, selects no exit
  value, and touches no strategy. Restoring the approved band, or re-deriving the naive gate, is a
  **P2.2.6 decision requiring explicit approval**.

## 3. orders_12 / orders_01 / orders_18 identical-signal finding — verified

Independently recomputed signal arrays via `index_daily_signals` (the real engine, unchanged), sorted
as `(signal_date, direction, spot)`:

| Candidate | # signals | Array identity |
|-----------|:---:|---|
| orders_12 | 12 | — |
| orders_01 | 12 | **identical to orders_12** (first 3: `2021-08-03 CE 16130.75`, `2022-01-17 CE 18308.1`, `2022-04-06 CE 17807.65`) |
| orders_18 | 12 | **identical to orders_12** |
| orders_05 | 54 | different |
| orders_07 | 50 | different |

* `orders_12 == orders_01` → **True**; `orders_12 == orders_18` → **True**; against `orders_05`/`orders_07` → **False**.
* The resulting **trade entry sets** (signal_date, expiry, strike; BASELINE Dev+Val) are likewise
  identical for 12/01/18 and differ from 05/07 — so the metric coincidence in the report
  (`orders_12 / 01 / 18` all `+237.8 / +235.1 / +231.1`) is genuine, not a reporting artefact.
* Note the three carry **distinct engine fingerprints** (`0eba5126`, `0007b9d6`, `e9a55da1`) — they are
  different strategies that happen to raise the same daily long/flat transitions on the single-instrument
  NIFTY index series. 12 raw signals → **11 executable entries** whole-sample (one is rejected for
  `NO_OPTION_BARS_ON_ENTRY`) → **9** in Dev+Val, matching the report's §3 "same 11 entry dates".
* This is a real **discrimination limit** of the harness (report §11), correctly disclosed; the audit
  confirms it rather than resolving it.

## 4. Integrity conclusions and required follow-up (no action taken here)

1. **Governance defect (must correct):** the P2.2.5 report's "Exits … `ExitConvention`, unchanged"
   (§1 L35) is inaccurate. The run convention (±30%/30% uniform) deviates from the approved
   (+15%/−8%, ratio-preserving) introduced at P2.2.3 without a recorded approval. **The label should
   be corrected and the deviation acknowledged.** The report title/conclusion of "unchanged methodology"
   is otherwise consistent.
2. **Not a look-ahead violation:** the substitution is a fixed a-priori symmetric band, not chosen on
   validation/holdout. No threshold, floor, or the protected holdout was used to pick it.
3. **Benchmark comparison is not like-for-like:** the `n=855` all-days naive-ATM must not be used as
   the "beats naive-ATM" bar for signal-timed candidates. The signal-matched hold-to-expiry
   comparison (§2.3) is the correct one and is provided.
4. **No strategy, parameter, or threshold was changed by this audit.** Restoring the approved band and
   re-basing the naive gate are **P2.2.6 decisions requiring explicit approval**; the approved value was
   *not* re-selected here and no holdout was consulted.
5. **Discrimination limit** (§3) is confirmed and remains a documented limitation.
