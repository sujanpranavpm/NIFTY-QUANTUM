## 1. Executive Summary & Audit Purpose

Milestone `P2.2.9.2` performs a strict technical audit and correction of the technical validation rules defined in `P2.2.9_TECHNICAL_VALIDATION_PLAN.md`.

In quantitative finance, technical validation rules must reflect actual market microstructure, exchange clearing mechanisms, and regulatory circulars. Applying inaccurate universal assumptions—such as asserting a single universal tick size of ₹0.05 across all instruments, assuming simple calendar-date boundaries for lot-size changes without accounting for overlapping contract cohorts, enforcing impossible balancing equalities on participant-wise reports, silently forward-filling missing intraday bars/OI, or applying arbitrary percentage bounds to non-like-for-like prices (EOD 30-minute VWAP vs last minute-bar close)—creates brittle, invalid data pipelines that either falsely reject clean historical market data or silently corrupt analytical feature matrices.

This audit rectifies five specific technical validation domains using primary-source evidence from official NSE circulars, contract specifications, and the repository's existing measured reference databases (`data/reference/`).

## 3. Audit Task 1: Instrument-Specific Tick-Size Specification

### 3.1 Primary-Source Evidence
1. **NSE Circular `NSE/FAOP/67135` (Contract Specifications - Index Derivatives):**
   - Establishes a price-step ladder for Index Level tick sizes:
     - Index Level $0 \le S \le 15,000 \implies$ Tick Size = ₹0.05
     - Index Level $15,000 < S \le 30,000 \implies$ Tick Size = ₹0.10
     - Index Level $S > 30,000 \implies$ Tick Size = ₹0.20
   - *Measured Exchange Reality (`data/reference/nifty_tick_sizes.csv` & `logs/p1_tick_grid.txt`):*
     - Throughout 2021–2026, the NIFTY index level was above 15,000.
     - **Traded Prices (Open, High, Low, Close):** 100% of traded option bars across all 318 official bhavcopy dates and all 23 historical provider expiry files remained on the **₹0.05 grid**.
     - **Settlement Prices (`SttlmPric` / `SETTLE_PR`):** Starting August 3, 2026, official daily settlement prices printed off the ₹0.05 grid and adopted the ₹0.10 step ladder per `NSE/FAOP/67135`.
2. **NSE Circular `NSE/FAOP/67134` (Contract Specifications - Stock Derivatives):**
   - Explicitly specifies: *"The stock futures shall have the same tick size as applicable for underlying security in CM Segment."*
   - In the Cash Market (CM) segment, tick size is governed by individual security price bands and series (e.g., standard equity tick is ₹0.05, but certain sub-₹100 securities or debt/preference series operate under different tick structures).
3. **Floating-Point Modulo Hazard:**
   - In standard IEEE 754 floating-point arithmetic, expressions such as `(18245.05 * 100) % 5` evaluate to `4.999999999999943` instead of `0`, causing false integrity rejections when evaluated with naive floating-point modulo operators.

### 3.2 Corrected Specification
- **Rule 1.1 (Dynamic Tick Resolution):** Tick size must never be hardcoded universally. The validator must resolve the expected tick size from an effective-dated instrument reference table (`data/reference/nifty_tick_sizes.csv`):
  - For NIFTY Index Options traded bars (`open`, `high`, `low`, `close`): Expected tick is **₹0.05**.
  - For NIFTY Index Options official settlement prices (`SttlmPric`): Expected tick is **₹0.05** prior to 2026-08-03, and **₹0.10** from 2026-08-03 onwards (for index level $15,000 < S \le 30,000$).
  - For Single-Stock Derivatives: Tick size must be dynamically inherited from the underlying CM equity master record.
- **Rule 1.2 (Exact Integer-Tick Representation & Decimal Pre-Check):** Floating-point modulo checks are strictly prohibited. As reconciled in P2.2.9.3, raw decimal precision must first be verified ($\le 2$ decimal places for decimal strings, or within $\epsilon = 10^{-5}$ tolerance for binary floats) to reject sub-paise corruption before integer conversion:
  $$\text{price\_paise} = \text{int}(\text{round}(\text{price} \times 100))$$
  $$\text{tick\_paise} = \text{int}(\text{round}(\text{expected\_tick} \times 100))$$
  $$\text{is\_valid} = (\text{price\_paise} \pmod{\text{tick\_paise}} == 0)$$

## 4. Audit Task 2: NIFTY Lot-Size History & Contract-Cohort Transitions

### 4.1 Primary-Source Evidence
A calendar-date lookup that assumes all contracts switch lot size simultaneously on a single calendar day is historically false. When the exchange revises board lots, existing contracts continue trading at their original lot size until their respective expiry dates, while newly listed contract cohorts trade at the revised lot size.

Evidence from official NSE circulars (`FAOP54334`, `FAOP64506`, `FAOP68747`), `fo_mktlots.csv`, `logs/lot_schedule.txt`, and official UDiFF bhavcopies (`NewBrdLotQty`):

### 4.2 Corrected Specification
- **Rule 2.1 (Contract-Level Resolution Key):** Lot size must be resolved at the contract level using the 4-tuple key:
  $$\text{ContractKey} = (\text{Symbol}, \text{ExpiryDate}, \text{StrikePrice}, \text{OptionType})$$
  In UDiFF bhavcopies, the authoritative per-row field `NewBrdLotQty` must be used directly.
- **Rule 2.2 (Fallback Hierarchy & Strict Labeling):**
  1. **Primary Authority:** Observed per-contract row lot (`NewBrdLotQty` in bhavcopy). (`estimated = False`).
  2. **Secondary Fallback:** Contract cohort lookup mapping expiry dates to their specific issuance regime. (`estimated = False`).
  3. **Tertiary Date-Only Fallback:** Modal date regime lookup (`data/reference/nifty_lot_history.csv`). Must be flagged with `estimated = True` and `basis = BASIS_DATE_REGIME`.
  4. **Fail-Closed Rule:** Any contract traded during dual-lot transition periods whose expiry cohort cannot be resolved must be marked `UNKNOWN` and rejected from strict financial validation.

## 5. Audit Task 3: Participant-Wise OI Reconciliation

### 5.1 Primary-Source Evidence
1. **Report Architecture (`fao_participant_oi_{DDMMYYYY}.csv`):**
   - Published by NSE Clearing Limited (NSCCL) at end-of-day for regulatory positioning transparency.
   - Contains 4 client categories: `Client` (Retail, HNI, Non-corporate), `DII` (Domestic Institutional Investors), `FII` (Foreign Portfolio Investors), `Pro` (Trading Member Proprietary Desks).
   - Columns span 6 instrument segments across Long and Short positions:
     - Future Index, Future Stock, Option Index Call, Option Index Put, Option Stock Call, Option Stock Put.
     - Summed into `Total Long Contracts` and `Total Short Contracts`.
2. **Reconciliation Realities:**
   - **Within a Participant Category:** Long positions NEVER equal Short positions (e.g., FIIs can hold 150,000 Long Index Futures and 45,000 Short Index Futures). Requiring internal equality per participant is mathematically invalid.
   - **Market-Wide Aggregate Equality:** While in cleared derivatives the sum of all long positions across the entire clearing house equals the sum of all short positions, publicly disseminated CSV reports can exhibit aggregate imbalances due to:
     - Custodial Participant (CP) accounts or unallocated clearing trades;
     - Footer/Total rows that combine non-clearing entries;
     - NSE Clearing reporting timing and post-session trade modifications.
   - NSE Clearing publishes no official documentation certifying that the published participant summary CSV must balance to zero at the aggregate contract level on every trading day.

### 5.2 Corrected Specification
- **Rule 3.1 (Strict Internal Row-Level Invariant):** For each participant row $i \in \{\text{Client}, \text{DII}, \text{FII}, \text{Pro}\}$:
  $$\text{Total Long}_i = \sum_{k=1}^6 \text{Long Segment}_{i, k}$$
  $$\text{Total Short}_i = \sum_{k=1}^6 \text{Short Segment}_{i, k}$$
  Any row failing internal arithmetic consistency must trigger immediate rejection (`FATAL_ROW_ARITHMETIC_ERROR`).
- **Rule 3.2 (Aggregate Market Reconciliation as Diagnostic Only):**
  The cross-participant sum:
  $$\Delta_{\text{market}} = \left| \sum_{i} \text{Total Long}_i - \sum_{i} \text{Total Short}_i \right|$$
  must be logged as a **DIAGNOSTIC RECONCILIATION METRIC**. It must **not** trigger a fatal batch rejection. If $\Delta_{\text{market}} > 0$, the batch is accepted with a diagnostic warning flag (`PARTICIPANT_OI_AGGREGATE_DISCREPANCY`).

## 6. Audit Task 4: Missing Intraday Bars and Stale/Zero OI Handling

### 6.1 Primary-Source Evidence
The quantitative repository's core architecture (`nifty_quant/derivatives/completeness.py`) explicitly forbids synthesizing candle prices or forward-filling open interest:
> *"The archive is not self-describing, so a gap can mean several very different things... Open interest is classified separately from prices: a bar can exist with open_interest == 0, which means the provider carried no OI observation for that minute, not that the contract had no positions. Neither case may be turned into a number by filling."*

In Indian options trading, deep OTM/ITM strikes routinely go 10 to 60 minutes without a trade. Representing a no-trade interval by synthesizing artificial OHLC bars or forward-filling last traded prices creates spurious volume and falsifies volatility models.

### 6.2 Corrected Specification
- **Rule 4.1 (Strict Zero-Imputation Policy):** Tradable OHLC prices must **never** be forward-filled or synthesized to force continuity.
- **Rule 4.2 (Granular Gap Taxonomy):** Every interval gap must be classified into one of five mutually exclusive states:
  1. `NO_TRADES`: The exchange reports the contract as active, but zero trades occurred during the minute bar. (Valid market state; no bar generated).
  2. `MISSING_DAYS`: The official bhavcopy indicates trading occurred, but the intraday file carries zero bars for that day. (Data defect; fail-closed rejection).
  3. `TRUNCATED_SESSION`: Minute bars exist for the morning, but cease prior to 15:25 IST. (Session truncation; exclude day from intraday strategy backtests).
  4. `MARKET_WIDE_HALT`: Documented technical trading halts (e.g., February 24, 2021). (Accepted without defect tagging upon holiday/halt calendar verification).
  5. `UNKNOWN_ABSENCE`: Missing observations without exchange corroboration. (Fail-closed quarantine).
- **Rule 4.3 (Open Interest State Separation):**
  - `Zero OI` (`open_interest == 0`): Represents a missing or unrecorded provider OI observation. It must be tagged `UNOBSERVED_OI` and excluded from OI-based feature calculations.
  - `Unchanged OI`: Repeated OI across consecutive bars is normal during quiet intervals and must not be treated as a data anomaly.

## 7. Audit Task 5: EOD Close vs 30-Minute VWAP Comparison

### 7.1 Primary-Source Evidence
1. **Official Exchange Definition of EOD Close (`ClsPric`):**
   - Under NSE equity and derivatives trading regulations, the official daily closing price is the **Volume Weighted Average Price (VWAP)** of all trades executed during the final 30 minutes of the trading session (15:00:00 to 15:30:00 IST).
   - If no trades occur between 15:00 and 15:30, the closing price defaults to the last traded price (`LastPric`), or prior settlement price.
2. **Minute-Bar Close (15:29 Bar):**
   - The close of the 15:29 intraday candle is the price of the final trade executed between 15:29:00 and 15:29:59 IST.
3. **Mathematical Incompatibility:**
   - In volatile market regimes or on high-gamma index options, the 15:29 last traded price can legitimately diverge by 5%, 15%, or 30% from the 30-minute VWAP.
   - Enforcing an arbitrary threshold (e.g., absolute difference $\le 2.5\%$) as an integrity gate falsely rejects valid options datasets.

### 7.2 Corrected Specification
- **Rule 5.1 (Classification as Diagnostic Metric):** The comparison between the 15:29 minute bar close and the official bhavcopy `Close` is classified as **DIAGNOSTIC ONLY**.
- **Rule 5.2 (Like-for-Like Comparison):**
  - If trade-level tick data is unavailable to recompute the 30-minute VWAP, no numeric threshold check may be used as a hard gate.
  - The appropriate sanity check is to verify that the 15:29 bar close falls within the daily bhavcopy range:
    $$\text{LwPric}_{\text{EOD}} \le \text{Close}_{15:29} \le \text{HghPric}_{\text{EOD}}$$
  - The percentage divergence $|\text{Close}_{15:29} - \text{ClsPric}_{\text{EOD}}| / \text{ClsPric}_{\text{EOD}}$ is tracked solely as an informational tracking metric (`eod_vwap_drift_pct`).
