## 1. DTE histogram discrepancy — resolved before coding

P2.2.2.1 left three competing "days-to-expiry" rulers that produced different histograms.
They are reconciled as follows.

| Ruler | Definition | Window spanned | Verdict |
|---|---|---|---|
| (a) within-file print-days | count of *distinct `trading_day`s present in a single expiry candle file* between entry and expiry | per-file only | **Understates** DTE — a contract skips sessions, so calendar gaps are silently dropped. Not a DTE ruler. |
| (b) official bhavcopy expiry calendar | effective-dated expiry reference from NSE bhavcopy | **2024-01-01 → 2026-11-03 (318 sessions)** only | Correct **on its coverage**, but collapses every pre-2024 expiry to DTE 0 because it has no sessions before 2024. Cannot measure DTE over the full data window. |
| (c) **index trading-session series** | every NIFTY index session in the assembled dataset | **2021-05-24 → 2026-07-02 (1,262 sessions)** | **Chosen ruler.** Continuous over the whole window; DTE = number of index sessions strictly after entry up to expiry. |

**Cross-check that settles the choice:** on the region where rulers (b) and (c) both exist
(2024+), the two agree on **99** expiry days and disagree on **0**. The index-session ruler
therefore reproduces the official-calendar answer wherever the official calendar is valid,
and extends it back to 2021 where it is not.

### Eligible-entry count at MIN_DTE = 2, measured at D+1

`DTE` is measured **at the actual entry session `D+1`** (the session after the signal day
`D`), never at the signal day — the option is bought at `D+1`, so that is where the
remaining-life test must land. Expiry-day entries are excluded by construction (`expiry >
entry`), and MIN_DTE = 2 excludes single-session entries.

Reproduced from code (`OptionTradeAdapter.eligible_entry_stats()`, `resolution="15m"`):

```
usable_expiry_files    : 22        (2026-08-04 stub is unreadable and skipped)
distinct_option_days   : 167       (days on which any option traded)
index_sessions         : 1262      (the DTE ruler, 2021-05-24 .. 2026-07-02)
overlap_option_days    : 158       (option days that are also index sessions)
dte_ladder_overlap_days: dte_ge_0 = 158, dte_ge_1 = 138, dte_ge_2 = 122, dte_ge_3 = 108
min_dte_at_entry       : 2
eligible_entry_days    : 121       (>=2 DTE at D+1 with a valid prior session)
```

The 121 eligible entry days split **84 dev / 18 validation / 19 holdout** (unchanged from
the P2.2.2.1 partition, now computed on the index-session ruler).

> **Bottom line:** the discrepancy was a *ruler* problem, not a data problem. On the
> index-session ruler, **121** D+1 sessions are eligible at MIN_DTE = 2. How many are
> actually *executable* is far smaller (see §5) because the option data is sparse — that
> sparsity is reported honestly, not hidden.

## 2. Pipeline

```
daily NIFTY signal (real engine, strategy UNCHANGED)
   -> deterministic CE/PE selection
   -> strike + expiry selection (effective-dated references, MIN_DTE at D+1)
   -> 15m option bars (timestamp-anchored entry)  [5m for sensitivity]
   -> premium-based ExitRules (fixed convention)
   -> OptionsExecutionEngine (next-bar, stop-wins, adverse-gap, UNRESOLVED)
   -> IndiaOptionsCommission (P2.1.2 cost levels, brokerage excluded by default)
   -> per-trade + per-rejection records (persisted)
```

New package **`nifty_quant/options/`** (all new files; no existing module edited):

| Module | Responsibility |
|---|---|
| `data.py` | `MarketData` — index daily bars from `data/raw/p1_sample/index__NIFTY.parquet`; the session ruler; per-expiry option candle files (unusable stubs skipped). |
| `reference.py` | `OptionReference` / `EffectiveLookup` — DTE on the index-session ruler; effective-dated `board_lot` / `tick_size` / `strike_interval` with an `estimated` flag + provenance; `expiry_candidates` at MIN_DTE. |
| `signals.py` | `index_daily_signals` — runs the **strategy through the real `run_backtest`** and reads `positions`; a `flat -> long` transition *is* the daily signal day `D`. |
| `selection.py` | `select_contract` — direction→CE/PE, nearest expiry with DTE≥min **at entry**, ATM strike on the effective interval, strike/expiry fallback, all fallbacks recorded. |
| `bars.py` | `build_option_bars` — filters one contract, orders by `(trading_day, candle)`, **maps entry by timestamp** to `D+1`, marks expiry on the last expiry-session bar, appends an unobservable expiry sentinel when the contract did not print. |
| `pipeline.py` | `OptionTradeAdapter` / `AdapterConfig` / `ExitConvention` / `RunResult` — wires everything; three execution scenarios; per-trade cost verification; summary. |
| `records.py` | `TradeRecord` / `RejectionRecord` / `RecordSet` / `persist_run` — per-trade fields (Req 10) and per-rejection reasons (Req 9) as parquet + CSV + JSON. |

Runner (reproducibility only): `scripts/_p223_run_adapter.py`.

## 3. Requirements — how each is met

1. **Strategies unchanged.** Signals are extracted by calling the strategies through
   `run_backtest` exactly as the equity engine does. `git diff` shows **zero tracked-file
   modifications** — no strategy, engine, or cost module was edited.
2. **Timestamp mapping, not integer indices.** The engine enters at
   `bars[signal_index + 1].open`. `entry_index` is the *first bar whose `trading_day` equals
   the entry session `D+1`*; `signal_index = entry_index − 1` (a real earlier bar). The daily
   signal list is never indexed into the bar list.
3. **15m primary, 5m sensitivity.** `AdapterConfig.resolution="15m"`,
   `sensitivity_resolution="5m"`; both run (see §5).
4. **MIN_DTE = 2 at actual entry.** Enforced in `expiry_candidates`/`select_contract` on the
   `D+1` session; a belt-and-braces re-check rejects anything below min at record time. All
   executed trades show `dte_at_entry ∈ {2,4,5,6}`.
5. **Effective-dated references.** `board_lot`/`tick`/`strike_interval` are looked up **as of
   the entry session**, each carrying `estimated` + provenance. Where no effective-dated
   strike interval covers the date (pre-2024, before the bhavcopy arbiter), selection falls
   back to a **data-implied** grid (smallest gap between traded strikes) — never a guessed
   spec — and records `strike_interval_source = data_implied`.
6. **Volume-unit-aware liquidity.** The conservative floor is scaled to `lot_size × lots`
   **share-equivalents** (the preset `1.0` is one share, not a tradable exit); optimistic /
   baseline keep the gate disabled (`0.0`).
7. **Engine safeguards preserved.** Next-bar entry, stop-wins-on-collision, adverse-gap
   `min(stop, open)`, and the `UNRESOLVED` state (expiry bar unseen) are the engine's own —
   used verbatim, not reimplemented.
8. **P2.1.2 cost discipline preserved.** The same `IndiaOptionsCommission` (default
   `brokerage='none'`) is passed to the engine, so `net_pnl` is net of statutory costs, and
   every trade carries `statutory_verified` / `all_in_verified` / `brokerage_excluded` /
   `cost_basis`. Pre-Oct-2024 slab-era dates fail closed (`statutory_verified=False`). A
   brokerage-excluded figure is never labelled net profit.
9. **Every rejection recorded.** Each rejected signal becomes a `RejectionRecord` with a
   reason and stage (selection / bars / execution).
10. **Per-trade persistence.** Strategy, direction, contract symbol, strike, expiry, DTE,
    moneyness, signal/entry/exit dates, lot, lots, scenario, status, entry/exit premium,
    gross/net PnL, costs, and all verification flags.

## 4. Fixed exit convention (not tuned)

`ExitConvention(stop_fraction=0.30, target_fraction=0.30, max_hold_bars=None)`: stop =
`entry_open × 0.70`, target = `entry_open × 1.30`, both rounded to the effective tick. This
is a **convention applied identically to every candidate** so exits are comparable — it is
explicitly *not* optimised and no parameter search was run.

Execution scenarios are the three P2 presets (0 / 2 / 5 bps slippage). The summary records
verbatim: **"0/2/5 bps are ESTIMATED execution assumptions, not measured fills."**

### Adapter run on the five Tier-1 strategies (15m, MIN_DTE=2 at D+1)

Persisted to `artifacts/p223/` (`trades.csv|parquet`, `rejections.csv|parquet`,
`summary.json`, `run_summary.json`).

| Strategy | trades | rejections |
|---|---|---|
| orders_12 | 6 | 10 |
| orders_01 | 6 | 10 |
| orders_18 | 6 | 10 |
| orders_05 | 12 | 50 |
| orders_07 | 9 | 47 |

* 39 trade rows = **13 unique entries × 3 scenarios**; `status` is `FILLED` for all.
* `option_type` is **CE only** — every Tier-1 strategy is long-only, so no PE is ever raised
  (PE selection exists and is tested, but these strategies do not generate short signals).
* `dte_at_entry ∈ {2, 4, 5, 6}` — MIN_DTE = 2 at entry holds for every trade.
* **Verification levels preserved:** `brokerage_excluded = True` on all 39;
  `statutory_verified = True` on **21/39** (the 2024+ dates), the rest fail closed on the
  pre-Oct-2024 slab era; `all_in_verified = True` on **0** (brokerage excluded is never
  all-in). Sample row: `orders_12 … 24000CE … lot 25 … STOP_LOSS … statutory-only`.
* **Rejections by reason:** `NO_OPTION_BARS_ON_ENTRY` 116 · `DTE_BELOW_MIN` 9 ·
  `ANCHOR_MISSING` 2. The dominant reason is **data sparsity** — on most signal days no
  eligible option contract printed a bar at `D+1`, so nothing is fabricated.
* **5m sensitivity:** identical trade/rejection counts (13 unique entries, 39 rows). The
  stops/targets resolve on the same decision bars for this sparse set, so the result is
  resolution-independent here; this is reported, not interpreted as an edge.

## 6. What this is *not*

* **No winners.** 13 unique executable entries across five strategies is far too thin to
  rank anything. The honest finding is that the zero-cost option data supports only a
  handful of testable entries — consistent with P2.2.2.1's "insufficient evidence" verdict.
* **No optimisation, no strategy edits, no live trading, no paid data, no
  dashboard/broker.** None of these were touched.
* **No fabricated fills.** Every "no data" case is a recorded rejection, never a synthetic
  price.
