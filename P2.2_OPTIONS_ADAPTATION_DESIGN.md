# P2.2.2 — NIFTY Options Adaptation Design

Date: 2026-11-06 · Baseline commit: `03a5d27` (clean) · Budget: ₹0 · Companion:
`P2.2_DATA_FEASIBILITY_REPORT.md`, `P2.2_BACKTESTING_METHODOLOGY.md`.

**This is a design, not an implementation.** No strategy is modified, no parameter is
optimised, no code is written here. It specifies *how* a Tier-1 daily index signal would be
turned into a simulated long NIFTY CE/PE trade by **reusing components that already exist**:
`engine/options_execution.py` (`OptionsExecutionEngine`, `OptionBar`, `ExitRules`),
`engine/options_costs.py` (`IndiaOptionsCommission`), `derivatives/calendar.py`
(`NiftyReference`, `ExpirySchedule`), `derivatives/coverage_registry.py`,
`derivatives/timestamps.py`, `strategies/contracts.py` (`size_standard_lots`).

Legend: **[FACT]** = already built/verified in-repo · **[ASSUMPTION]** = declared modelling
choice · **[LIMITATION]** = honest bound.

---

## 1. The gap this design closes (and does not fake)

> **[FACT]** `OptionsExecutionEngine` already simulates *one long option trade* given a bar
> sequence, a `signal_index`, premium `ExitRules`, `lots`, `lot_size`, and a scenario. But
> **no strategy emits an option order today**, and nothing maps "orders_12 flipped bullish on
> day D" → "buy *this* CE at D+1 open, stop at *this* premium, target *this* premium".
> **[LIMITATION]** That **adapter** is the only genuinely new (to-be-built) piece. This
> document defines its deterministic rules; it does not implement it.

The five Tier-1 candidates contribute a **direction** (and, for orders_12, an explicit
reward/risk shape). Everything about *which contract* and *how it is filled/costed* is supplied
by the common framework below — identically for all five (fair comparison, §6 of the
methodology).

## 2. Options contract selection — deterministic rules

Inputs allowed at decision time (bar D close, before entry): the NIFTY index level on D,
the **effective-dated** strike grid, the listed-expiry set, and each candidate contract's
*observable* premium/volume/OI up to and including D.

### 2.1 CE vs PE (option type)

**[FACT]** Direction comes from the strategy signal.

| Signal at D | Contract bought at D+1 open |
|-------------|-----------------------------|
| Bullish / long flip (01, 05, 07, 12, 18 upside) | **Buy CE** (call) |
| Bearish flip where the strategy defines a downside leg | **Buy PE** (put) |

* orders_01/18 as coded are **long-only** on the underlying: they can only ever indicate a CE
  (or flat). A PE leg is *not* implied by their current logic — **[LIMITATION]** adding a
  downside rule would be a *modification*, out of scope now. So on current logic these
  candidates research **CE buying** (and flat); this asymmetry is reported, not hidden.
* **[ASSUMPTION]** "Bullish" = the strategy's long signal; no separate market-view overlay is
  invented.

### 2.2 Strike selection

**[FACT]** ATM reference = the strike minimising `|strike − index_close(D)|` on the day's
`NiftyReference.strike_interval(D)` grid (1000 in 2024–25, 500 / 50 in 2026). Ties broken by
the **nearer-the-money** strike, then the **higher traded volume on D**, then the lower strike.

**Eligibility band (fixed a priori, identical for all candidates):**

| Bucket | Definition (calls; puts mirror on the other side) |
|--------|---------------------------------------------------|
| ATM | nearest strike to `index_close(D)` |
| ITM | strike < index level (call) |
| OTM | strike > index level (call) |

**[ASSUMPTION]** Default research moneyness = **ATM ± 1 strike** band, entry at the single
**most-liquid qualifying strike** (ranked by D-tday traded volume, then OI). The band is a
declared choice; it is *not* tuned to results (methodology §5 forbids holdout-driven tuning).

**[LIMITATION]** **No IV, no Greeks, no delta target.** The repo stores no volatility surface
(see feasibility §7), so selection uses **only** observable price/volume/OI. Any
"pick the 0.5-delta strike" or "cheapest gamma" rule would require invented data and is
**excluded by design**. Delta/IV-based selection is listed as a future prerequisite, not a
present rule.

### 2.3 Expiry selection

**[FACT]** Candidate expiries are those **listed on D** per `ExpirySchedule` / observed
`nifty_expiry_dates.csv`; weekday cadence (Thu→Tue at 2025-09-01) is read from
`nifty_expiry_cadence.csv` **as-of D**, never hard-coded.

**[ASSUMPTION]** Rule: choose the **nearest expiry whose date > D** that satisfies
`days_to_expiry ≥ MIN_DTE`, **measured at the actual entry session D+1, not the signal date D**,
with **MIN_DTE-at-entry = 2 trading sessions** (declared a priori so a position survives at least
one bar after entry rather than being forced straight into expiry settlement) *and* passes
availability (§2.4). **Expiry-day entries (DTE-at-entry = 0) are excluded from the primary
experiment** — 22 such file-days; DTE=1 entries are reported separately, never merged. If the
front expiry is unavailable/illiquid, fall to the next listed expiry; if none qualifies, **no
trade** (fail-closed). This deliberately biases toward short-DTE contracts because that is *what
the data contains* (feasibility §3.1: median calendar DTE ≈ 6 days) — a bound, not a preference
tuned for profit. **[CORRECTED in P2.2.2.1: was "MIN_DTE = 1 session" measured on the signal day.]**

**[LIMITATION]** The sampled archive is mostly the **last ≤2 weeks before expiry**, so on
entry dates most selectable expiries are already short-DTE (theta-heavy). This is inherent to
available data and must be reported per trade (`dte_at_entry`).

### 2.4 Contract availability checks (all fail-closed)

Before an entry is allowed, the chosen (expiry, strike, type) must, on **D+1**:
1. **[FACT]** exist in the coverage registry as a non-missing, non-inactive contract-day, and
   `assert_no_silent_skip()` must be clean for the key;
2. **[FACT]** sit in a `STRICT_OK` session (or an explicitly accepted `NO_CLOSING_PRINT`);
3. **[FACT]** have an `OptionBar` with `available=True` and positive-finite OHLC (the dataclass
   raises otherwise) and `volume ≥` the scenario liquidity floor;
4. **[FACT]** carry a resolvable `board_lot(D+1)` and `tick_size(D+1)` from the `ParameterStore`.

If any check fails the entry is **NO_ENTRY** — never a fabricated fill. **[LIMITATION]** On the
~158 joint days these checks will frequently reject thin strikes/far expiries; low fill counts
are an honest output.

**[FACT] No future information.** Every input above is stamped ≤ D+1 open and enforced by the
open-label convention (`timestamps.py`) and the EOD-leakage guard (`units.assert_no_eod_leakage`).
The engine's `signal_index+1` entry and "anchor on best *prior* bar high" trailing (`ExitRules`
docstring) structurally bar look-ahead.

## 3. Execution model (reuse of `OptionsExecutionEngine`)

**[FACT]** The following are *already implemented and pinned*; the design consumes them as-is.
Nothing here re-derives execution logic.

| Aspect | Rule | Where |
|--------|------|-------|
| Signal timestamp | Computed after bar D close (open-labelled: D's data covers `[D, D+1)`). | `timestamps.CONVENTION` |
| Earliest permitted entry | **Bar D+1 open** (`entry_index = signal_index+1`); never the signal bar's close. | `run()` |
| Entry pricing | `entry_bar.open` shifted against the trader by `scenario.adverse_slippage_bps`. | `_adverse()` |
| Exit evaluation window | From `entry_index+1` onward — a position is never entered *and* left inside one candle. | `run()` |
| Stop-loss / target | **Premium-denominated** `ExitRules.stop_premium` / `target_premium`; trail via `trail_amount`/`trail_percent` anchored on prior-high. | `ExitRules` |
| Stop vs target collision | **Stop wins** (conservative, identical across scenarios). | `run()` |
| Gap through stop | Fills at the **worse** price `min(stop, open)` for a sell; never the hoped stop level. | `run()` |
| Target fill | Sells at the limit (no favourable gap-up credited). | `run()` |
| Time exit | `max_hold_bars` → exit at bar close (adverse). | `run()` |
| Expiry handling | On an `is_expiry` bar exit at close (adverse), reason `EXPIRY_SETTLE`. | `run()` |
| Expiry on a missing bar | Return **UNRESOLVED** (no fabricated settlement price). | `run()` |
| Missing bar (not expiry) | `continue` — nothing fills inside an unobservable interval. | `run()` |
| Liquidity floor | Exit below `scenario.min_exit_volume` is **rejected** (stays open), not skipped. | `run()` |
| End of data, still open | `OPEN_AT_END`, marked at last available close (or `None`). | `run()` |
| Slippage | Only via the three scenario presets; no hidden extra haircut. | `config` §4 |

**[CORRECTED in P2.2.2.1] Resolution & hold semantics.** **[FACT]** Option candles exist at
1m/5m/15m (30m is never produced). **[ASSUMPTION]** The **primary experiment runs on 15-minute
premium candles**, with **5-minute as a robustness sensitivity** — measured basis: 26.0% of 1m
bars are degenerate (`open==high==low==close`) on thin strikes vs 6.7% at 15m, so a 1m premium
stop/target fires on non-moves. `max_hold_bars` counts **bars of the chosen resolution**, so a
time-exit must be stated in **sessions** and converted via candles/day (25/day at 15m, 75/day at
5m); the same integer means different elapsed time across resolutions.

**[CORRECTED in P2.2.2.1] Liquidity floor is unit-critical.** **[FACT]** `OptionBar.volume` is in
**share-equivalents (contracts × lot)**, so the CONSERVATIVE preset's `min_exit_volume = 1.0` is
**1 share-equivalent** — measured, every nonzero bar on a liquid strike is ≥1 contract (≥25 sh,
median ≈3,200 sh) — hence the `1.0` floor **rejects essentially nothing and is not a meaningful
liquidity test**. **[RULE]** the adapter must re-express the floor as **`lot_size × lots`
share-equivalents** (at least the whole exiting position observed in that bar); until then
CONSERVATIVE's gate is cosmetic and must be labelled as such. Missing minute bars are **absent
rows**, treated as `available=False` (no fill) — never zero-volume placeholders.

**Premium risk mapping (the adapter's only exit job).** **[ASSUMPTION]** Convert a strategy's
underlying-relative idea into premium levels *at entry sizing time only*, e.g. orders_12's
`+6%/−3%` bracket becomes `target_premium = entry_premium·(1+0.06·k)` /
`stop_premium = entry_premium·(1−0.03·k)`. Because option premium is levered and non-linear,
`k` (premium gearing) is **not observable from stored data** (no IV/Greeks), so the honest
default is a **fixed premium-percentage band declared up front** (e.g. TP +15% / SL −8% of the
entry premium) applied identically to all five candidates — with each strategy's *own* reward/
risk *ratio* preserved where it defines one (orders_12's 2:1). **[LIMITATION]** This is a
declared approximation, **not** a Greeks-correct translation; it is never tuned to results.

**Sizing.** **[FACT]** `size_standard_lots` / fixed `lots` with `lot_size = board_lot(D+1)`.
**[ASSUMPTION]** One contract unit per signal (lots held constant, e.g. 1) for the screening
design so P&L is comparable across candidates; risk-budget sizing is a later option, not now.

**Partial exits.** **[LIMITATION]** `run()` models a **single full** entry→exit; the *cost*
module prorates per leg correctly, but multi-scaled/partial exits and multiple concurrent
positions per candidate are **not** in the current engine. The methodology therefore evaluates
one-position-at-a-time per contract and flags partial-exit handling as an unbuilt extension.

## 4. Cost model (reuse of `IndiaOptionsCommission`)

**[FACT]** Charges are assessed on **premium turnover** `premium × lot_size × lots`, entry and
exit legs separately, from the effective-dated P2.1.2 schedule: STT on the option *seller*
(exit), stamp duty on the *buyer* (entry), exchange-txn + IPFT + SEBI each side on premium, GST
on the fee base, brokerage configurable. `round_trip()` returns the itemised total.

### 4.1 The four verification levels — never conflated

**[FACT]** The engine exposes distinct verdicts; the design mandates reporting all of them:

| Flag | Meaning |
|------|---------|
| `statutory_verified` | Every statutory rate used was independently sourced (brokerage irrelevant). |
| `brokerage_verified` | The configured broker fee is attested against a published tariff. |
| `brokerage_excluded` | `brokerage.model = "none"` — **no** broker fee attributed (the ₹0 default). |
| `all_in_verified` | `statutory_verified` **AND** `brokerage_verified` — a *fully net* cost. |

### 4.2 Reporting rule (hard)

* **[FACT]** Current config default is **brokerage model `"none"`, `verified=False`** → every
  trade is `brokerage_excluded=True`, `all_in_verified=False`.
* **[FACT]** The `cost_basis` label for that state literally reads: *"statutory-only (brokerage
  excluded; NOT fully all-in net — do not label as net profit)"*.
* **RULE:** Any P&L produced here is **"statutory-only, brokerage-excluded"**, **never**
  "net profit". A number may be called fully all-in net **only** when `all_in_verified=True`.
  Presenting a `brokerage_excluded` result as net profit is prohibited.

### 4.3 Residual statutory uncertainty (fail-closed)

* **[FACT]** Two pre-Apr-2023 slab-era `exchange_txn` rows remain `estimated=True` (marginal
  tier needs member monthly turnover, which a research book lacks). A trade priced on those
  rows → `statutory_verified=False`, `cost_basis = "modelling only"`.
* **[LIMITATION]** Consequently the option readiness gate `transaction_costs_verified` is
  **fail-closed**; option results are **modelling-grade**, not strict-financial-validation,
  until that gate is legitimately satisfied — a limit to respect, not a defect to hide.

### 4.4 Scenario slippage (kept separate from statutory cost)

**[FACT]** Slippage is *not* folded into the statutory schedule; it is the `ExecutionScenario`
`adverse_slippage_bps` applied at fill (**[ASSUMPTION]** `IndiaOptionsCosts.slippage_pct` stays
at its neutral `0.0` default so the two mechanisms never double-count). **[CORRECTED in P2.2.2.1 —
labelling]** The 0 / 2 / 5 bps values are **estimated adverse-selection haircuts chosen as
sensitivity knobs, *not* measured execution cost**: the repo has no bid/ask or trade tape to
estimate real slippage, so every document must call them *estimates*, never *observed fills*.
Presets:

| Scenario | adverse_slippage_bps | min_exit_volume |
|----------|---------------------:|----------------:|
| A_OPTIMISTIC | 0.0 | 0 (gate off) |
| B_BASELINE | 2.0 | 0 |
| C_CONSERVATIVE | 5.0 | 1.0 |

A candidate must be judged on **BASELINE/CONSERVATIVE**, not on OPTIMISTIC alone (methodology §6).

## 5. Confirmed vs assumed vs unresolved (this design)

**Confirmed ([FACT])** — execution engine, cost engine, effective-dated calendar/lot/tick/
strike stores, coverage + completeness gates, open-label convention, next-bar safeguards, four
verification levels, three scenarios — all already in the repo.

**Assumptions ([ASSUMPTION])** — ATM±1 moneyness band; front-nearest-eligible expiry; **15m
primary resolution (5m sensitivity)**; fixed premium-percentage TP/SL band (**+15%/−8%**)
preserving each strategy's reward/risk *ratio*; one-lot position; index-1m resampled with the
same open-label convention; **MIN_DTE-at-entry (D+1) = 2 sessions, expiry-day entries excluded**.

**Unresolved ([LIMITATION])** — no IV/Greeks (so no delta/IV selection, no gearing-exact
premium risk); single-position/no-partial-exit engine; brokerage excluded & some statutory rows
estimated ⇒ **modelling-only** costs; tiny joint-sample bounds trade counts; long-only current
logic ⇒ PE research requires a (future) modification.
